# FB-026 — Headless-Runtime-API

**Was:** Vier Endpunkte unter `/api/public/v1` für fremde Frontends, die die Strecke
selbst rendern:

| Methode | Pfad | Zweck |
| --- | --- | --- |
| `GET` | `/funnels/{token}` | Struktur der veröffentlichten Fassung |
| `POST` | `/funnels/{token}/sessions` | Sitzung beginnen oder fortsetzen |
| `PATCH` | `/funnels/{token}/sessions/{session}/answers` | Antworten prüfen, nächsten Schritt liefern |
| `POST` | `/funnels/{token}/sessions/{session}/submit` | Anfrage abschließen |

**Der Kern der Änderung ist kein Endpunkt, sondern eine Extraktion.** Der Ablauf einer
Strecke — validieren, vereinheitlichen, Weg bestimmen, Punktzahl, Ergebnis, Spam-Prüfung,
Übergabe — lag in der Livewire-Komponente. Ihn in der API nachzubauen hieße, zwei
Runtimes zu pflegen, die zwangsläufig auseinanderlaufen: Ein fremdes Frontend sähe dann
eine andere Verzweigung oder eine andere Punktzahl als unsere eigene Strecke, und niemand
könnte sagen, welche stimmt. Der Ablauf liegt deshalb jetzt in
`App\Funnel\Runtime\FunnelRunService`; Livewire-Komponente und Controller sind beide
dünn und rufen denselben Dienst.

**Adressierung ohne IDs:** Der Funnel über `public_token`, die Sitzung über ihren
ULID-Token. Eine fortlaufende Nummer nach außen zu geben hieße, fremde Sitzungen erraten
zu können. Ausgeliefert wird der Snapshot unverändert — er enthält von Haus aus keine
Datenbank-IDs.

**Gleiche Regeln wie die eigene Strecke:** Validierung über die Fragetyp-Handler
(FB-011), Wegfindung über den `StepResolver` (FB-012), Punktzahl und Ergebnis aus FB-013,
Spam-Regeln aus FB-023 inklusive Honigtopf-Feld `website`, Herkunftsprüfung aus FB-025
über dieselbe `EmbedOriginPolicy`. Auch der Kontaktschritt wird geprüft — ein fremdes
Frontend darf Kontaktdaten nicht ungeprüft einliefern.

**Warum die Herkunftsprüfung mit 403 arbeitet und nicht über CORS-Header:** Ein
`Access-Control-Allow-Origin` schützt nur den Browser eines Besuchers davor, eine fremde
Antwort zu lesen — ein Aufruf ohne Browser ignoriert ihn vollständig. Wer eine Allowlist
über Header durchsetzen wollte, hätte gar keinen Schutz. Antwortet der Server dagegen mit
403, gibt es nichts zu lesen, unabhängig vom Header.

**Ratenbegrenzung:** eigener Limiter `funnel-public`, gezählt je IP-Hash aus FB-022 gegen
`config('funnel.public.rate_limit_per_hour')` — derselbe Schwellwert wie in der
eingebetteten Strecke.

**Neue Config-Keys:** keine. **Migrationen:** keine — die API arbeitet auf den Tabellen
aus FB-021 und FB-014.

**Der wichtigste Test vergleicht beide Wege:** Derselbe Funnel wird einmal über die
Livewire-Strecke und einmal über die API durchlaufen, mit denselben Eingaben. Antworten,
Punktzahl, Ergebnisschlüssel, Funnel-Fassung und der protokollierte Weg müssen
übereinstimmen; nur die Sitzung ist naturgemäß eine andere. Liefe die API auf eigener
Logik, fände man den Unterschied sonst erst, wenn ein Kunde über die API andere
Ergebnisse bekommt als über die eingebettete Strecke — und dann in Produktionsdaten.

Nebenbei aufgeräumt: Die Livewire-Komponente ist von 497 auf rund 340 Zeilen geschrumpft,
und die Ereignisfolge einer Sitzung hat einen überflüssigen `step_complete`-Eintrag
verloren — der Ergebnis-Screen ist eine Zwischenanzeige, kein eigener Schritt.
