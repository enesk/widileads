# FB-030c — Lebenszyklus über die Management-API

**Was:** Fünf Endpunkte — `POST /funnels/{funnel}/publish`, `/duplicate`, `/archive` sowie
`GET /funnels/{funnel}/versions` und `/versions/{version}`.

**Warum kaum Code:** Veröffentlichen (FB-014), Duplizieren und Archivieren (FB-018)
existieren bereits als Actions. Der Controller ruft sie nur auf. Eine zweite Umsetzung
derselben Vorgänge wäre der sichere Weg, dass API und Oberfläche mit der Zeit
unterschiedliche Ergebnisse liefern — etwa eine Kopie, die über die API andere Felder
mitnimmt als über den Builder.

**Neu:** `funnel_versions.note` — ein Freitext zur Veröffentlichung, den die Spec
vorsieht. Ohne ihn beantwortet die Versionshistorie nur, *wann* veröffentlicht wurde,
nicht *warum*; bei einem Funnel, der über Monate läuft, ist genau das die Frage, wenn
eine Fassung zurückverfolgt werden muss.

**Scheiternde Veröffentlichung:** `FunnelNotPublishableException` trägt alle Gründe auf
einmal (FB-014). Sie kommen als 422 mit den Gründen unter `errors.funnel` zurück — es
sind Fachaussagen, keine Feldfehler, und der Aufrufer soll sie anzeigen können.

**Name und Slug einer Kopie** bestimmt weiterhin die Action, damit dieselbe Struktur
beliebig oft kopiert werden kann. Wer eigene Werte mitgibt, bekommt sie danach gesetzt;
die Eindeutigkeit prüft der Form Request.

**Adressierung der Version** über die Versionsnummer, nicht über die Datenbank-ID — das
ist die Nummer, die der Aufrufer in der Historie sieht.

**Neue Config-Keys:** keine.

**Migrationen:** `2026_09_07_143000_add_note_to_funnel_versions_table` — additiv, mit
`down()`, Minutenblock 30–44.

**Tests:** keine. Das Ticket berührt weder Geld noch Lead-Zustände, Maskierung,
Mandantentrennung, Nebenläufigkeit noch Signaturprüfung. Der Contract-Test aus FB-030a
deckt ab, dass alle fünf Operationen als Route existieren und dokumentiert sind.
