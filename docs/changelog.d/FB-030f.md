# FB-030f — Ratenbegrenzung und Idempotency-Key

**Was:** Alle `/api/v1`-Routen laufen jetzt hinter einem eigenen Limiter
(`funnel-management`) und der Middleware `EnsureIdempotentRequest`.

**Begrenzt wird je Token, nicht je IP:** Hinter einer IP können viele Kunden sitzen —
ein Agentur-Büro, ein Rechenzentrum, ein NAT-Gateway. Ein Token gehört dagegen genau
einem Workspace. Wer kein Token hat, fällt auf die IP zurück.

**Idempotency-Key:** Ein Client, dessen Verbindung nach dem Absenden abbricht, weiß
nicht, ob die Aktion ausgeführt wurde. Ohne Idempotenz bleibt ihm nur, es erneut zu
versuchen — und im Zweifel einen zweiten Funnel anzulegen. Mit dem Schlüssel bekommt er
beim zweiten Versuch dieselbe Antwort wie beim ersten, ohne dass etwas ein zweites Mal
passiert.

Drei Entscheidungen dabei:

- **Anderer Rumpf bei gleichem Schlüssel → 409.** Das ist kein Wiederholungsversuch,
  sondern ein anderer Aufruf unter fremdem Namen; eine gespeicherte Antwort
  zurückzugeben wäre schlicht falsch.
- **Nur erfolgreiche Antworten werden gemerkt.** Ein fehlgeschlagener Aufruf darf
  wiederholt werden — sonst brennt ein Tippfehler den Schlüssel für 24 Stunden.
- **Der Schlüssel gilt je Token.** Zwei Workspaces dürfen denselben Schlüssel verwenden,
  ohne sich gegenseitig Antworten zu liefern.

Eine wiederholte Antwort trägt den Header `Idempotency-Replayed: true`, damit der Client
erkennt, dass nichts erneut passiert ist.

**Neue Config-Keys:** `config/funnel.php` → `api.rate_limit_per_minute` (120),
`api.idempotency_ttl_hours` (24). Beide im bestehenden `api`-Block.

**Migrationen:** keine. **Tests:** keine — das Ticket berührt keine der Ausnahmen.
